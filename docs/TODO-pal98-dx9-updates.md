## 背景摘要

- `仙剑98DX9` 配置主要服务于 `PALDLL_DX9` 对应的仙剑98新补丁。
- 计时器核心原理是读取仙剑98进程内存，依据地图、坐标、物品、战斗敌人等状态判断节点是否完成。
- 当前节点推进是顺序制：只有当前节点满足 `Check()` 才会进入下一个节点。
- 通关条件应以最终击败拜月为准，拜月血量为 0 时主计时结束。
- `仙剑98DX9` 的改动原则上也应同步到 `仙剑98` 配置，避免两个核心行为继续分叉。

## P0: 主计时在部分电脑上不能居中

现象：

- 主界面截图 `snapshots\01.png` 下方最大的 `00:00:00` 是主计时。
- 在部分用户电脑上主计时视觉上不能居中。

初步定位：

- `GEX.BuildRects()` 当前将主时间和厘秒拆为两个区域：
  - `rcMainTimer`
  - `rcMainTimerMS`
- `DrawMainTimer()` 使用 `GLayout.sfFC` 绘制 `HH:MM:SS`。
- `DrawMainTimerMS()` 使用 `GLayout.sfFN` 绘制厘秒。
- 当前布局通过固定左边距、固定右侧厘秒区域估算，可能受 DPI、字体 fallback、系统缩放、字体度量差异影响。

建议实现方向：

- 把主计时整体视为一个视觉组合来居中，而不是分别让 `HH:MM:SS` 和厘秒依赖固定矩形。
- 使用 `Graphics.MeasureString` 或 `TextRenderer.MeasureText` 以当前字体测量：
  - `HH:MM:SS` 宽度
  - 厘秒宽度
  - 反作弊 `*` 宽度
- 根据总宽度计算组合起点，使整体中心对齐窗口或主计时可用区域中心。
- 保留现有样式设置、描边、双击区域和局部刷新逻辑。

验收点：

- 100%、125%、150% Windows 显示缩放下，主计时视觉居中。
- 不同字体、字号、窗口宽度下，主时间和厘秒不重叠。
- `*00:00:00` 反作弊状态也居中。
- 简版小窗口不出现文本裁切。

## P0: 游戏关闭后仍反复提示 DX9 窗口句柄无效

现象：

- 仙剑98关闭后，计时器有时仍不断提示：`请使用仙剑98 DX9移植版！窗口句柄无效`。
- 该问题只在固定几个人电脑上偶发。

初步定位：

- `仙剑98柔情DX9.GetPalHandle()` 中当 `Process.GetProcessesByName("Pal")` 找到进程，但 `MainWindowHandle == IntPtr.Zero` 且超过宽限期后，会设置 `cryerror`。
- 风险场景：
  - 进程退出窗口已销毁，但进程对象短时间仍存在。
  - 多 Pal 进程或旧 PID 状态未及时重置。
  - `cryerror` 没有在游戏消失或状态恢复时清空。

建议实现方向：

- 在设置“窗口句柄无效”前增加更严格的存活和主窗口校验：
  - `HasExited`
  - `MainWindowHandle`
  - `PID` 是否仍匹配
  - 必要时 `Refresh()` 后再读窗口句柄
- 游戏关闭时应清理：
  - `PalHandle`
  - `GameWindowHandle`
  - `PalProcess`
  - `PID`
  - `GMD5`
  - `DX9Version`
  - `InitialDetectionTime`
  - `HasConfirmedDX9`
  - `cryerror`
- 区分“启动过程等待 DX9 标题”和“游戏已关闭”：
  - 启动中可以静默等待。
  - 已确认过 DX9 后，如果进程/窗口消失，应停止读取并静默回到等待状态，不应弹错。

验收点：

- 关闭仙剑98后不再循环弹出窗口句柄无效。
- 正常启动 DX9 版本仍能识别。
- 非 DX9 版本或标题不匹配时仍能给出一次明确提示，但不刷屏。
- 多开 Pal 时仍能稳定选择正确进程或给出合理提示。

## P1: 支持跳图路线的非顺序节点推进

现状：

- `TimerCore.Checking()` 只检查 `CheckPoints[CurrentStep]`。
- 当前节点不满足时，即使后续节点已经满足，也不会跳过。

需求：

- 对跳地图玩法，允许后续节点先满足。
- 如果没满足当前节点但满足了后面的节点，应直接推进到对应节点之后。
- 被跳过的节点要保留区别颜色，不能伪装成正常完成。
- 最终击败拜月仍应结束计时。

建议实现方向：

- 为 `CheckPoint` 增加完成状态或元数据，例如：
  - 正常完成
  - 自动跳过
  - 手动跳过
  - 当前进行中
- `TimerCore.Checking()` 从当前节点开始扫描后续节点：
  - 优先检查当前节点。
  - 当前不满足时，可向后查找第一个满足的节点。
  - 对中间未满足节点标记为“跳过”。
  - 命中的后续节点标记为完成，并推进到下一节点。
- 建议提供开关，至少先仅对 `PAL98DX9` / `PAL98` 启用，避免影响其他游戏内核。
- 对“拜月血量为 0”这种终点条件应允许全局优先识别。

验收点：

- 正常路线行为不变。
- 跳过早期节点后，后续节点能触发并推进。
- 被跳过节点显示颜色与正常完成不同。
- 区间时间差、预计通关、导出成绩和插件事件不崩。
- 手动 `Jump()` 与自动跳过状态不互相污染。

## P1: “土”的检测失效且需要实时显示

现状：

- `仙剑98柔情DX9` 和 `仙剑98柔情` 中 `MaxTLF` 对应 `EarthPaper`。
- 战斗开始记录 `0x47` 土灵符，战斗结束时累加。
- 实时战斗显示目前只更新火、血、剑、夜行衣：
  - `CurrentBattleHCG`
  - `CurrentBattleXLL`
  - `CurrentBattleLQJ`
  - `CurrentBattleYXY`
- “土”没有对应实时临时变量，显示只依赖 `MaxTLF`。

建议实现方向：

- 增加 `CurrentBattleTLF`，逻辑与火、血、剑、夜行衣一致。
- `BattleBegin()` 继续记录 `0x47` 初始值。
- `Battling()` 中实时更新 `CurrentBattleTLF = biw.GettedCount(0x47)`。
- `GetMoreInfo()` 显示时使用 `MaxTLF + CurrentBattleTLF`。
- 确认 `0x47` 是否仍是新补丁下土灵符物品 ID；如失效，按 PALDLL_DX9 / Pal98Robot 的物品读取结果重新校对。

验收点：

- 战斗中获得土灵符后，“土”数值实时变化。
- 战斗结束后数值固化到 `MaxTLF`，不重复累加。
- 读档、云存档、导出成绩中的 `EarthPaper` 保持正确。
- `PAL98DX9` 和 `PAL98` 行为一致。

## P2: 评估从 VS2019 迁移到 VS2026 编译生成

现状：

- 当前开发环境主要使用 VS2019。
- 需要兼容 Win7 SP1 64 位用户环境。
- 希望未来可以改为 VS2026 编译生成，减少对 VS2019 环境的依赖。

需要先确认：

- VS2026 是否仍可稳定构建当前 .NET Framework 4.0 / WinForms 项目。
- 生成产物是否仍能在 Win7 SP1 64 位运行。
- 当前项目、依赖 DLL、ClickOnce/发布目录、OBS 插件相关项目是否有旧工具链限制。
- 如果 VS2026 默认 MSBuild / C# 工具链不再支持某些旧目标，需要评估是否改用独立 Build Tools、SDK-style 迁移或保留兼容构建脚本。

建议实现方向：

- 先建立一个“只构建不改功能”的 VS2026/MSBuild 验证分支。
- 固定目标框架和平台：
  - `TargetFrameworkVersion` 保持兼容现有运行环境。
  - x86 / AnyCPU / 64 位辅助进程分别确认。
- 将可重复构建命令写入文档或脚本，避免只依赖 IDE 点击生成。
- 在 Win7 SP1 64 位虚拟机或实机上验证主程序启动、自动计时、内存读取、改键器和插件加载。

验收点：

- 不安装 VS2019，仅使用 VS2026 或对应 Build Tools 可以完整编译。
- 生成的主程序可在 Win7 SP1 64 位运行。
- `PAL98DX9` 和 `PAL98` 内核可正常读取游戏内存。
- 改键器、插件加载、发布包生成不退化。
- 如果发现 VS2026 无法直接兼容，应记录保底方案，例如保留 VS2019 Build Tools、使用 CI 固定旧工具链，或逐步迁移项目格式。
